# 后端架构清理计划（app/）

本文档基于现有后端代码结构（FastAPI 单体、分层服务、统一配置）制定架构清理与演进计划，强调可落地、可验收、可回滚。

## 目标与范围

### 目标
- 降低启动/配置副作用，提升可测试性与可观测性。
- 统一数据访问与依赖注入模式，减少隐式耦合。
- 明确模块边界，减轻 `core/` 与 `services/` 的“万能”问题。
- 为后续拆分后台任务与性能治理奠定基础。

### 范围
- 仅覆盖 `app/` 后端服务；数据库迁移仍在 `backend/alembic/` 管理。
- 不涉及 OpenAPI/SDK 的生成流程修改。
- 不引入破坏性接口变更，除非明确标注与同步升级客户端。

## 里程碑与阶段规划

> 以 2 周为一个 Sprint 进行估算，可根据实际资源调整。

### 阶段 0：基线与风险清点（1 周）
- 目的：明确现状与改造边界，避免清理过程中引发不可控回归。
- 产出：基线文档与风险清单。

### 阶段 1：可观测性与安全日志（1~2 周）
- 目的：提升排障能力，降低敏感信息泄漏风险。

### 阶段 2：配置与启动治理（2~4 周）
- 目的：降低 import 副作用，统一启动与依赖加载流程。

### 阶段 3：数据访问统一与依赖注入（3~6 周）
- 目的：统一 async DB 模式，清理同步阻塞路径。

### 阶段 4：后台任务与模块边界清理（6~10 周）
- 目的：将重任务剥离出请求链路，明确核心与业务边界。

## 详细任务清单

### 阶段 0：基线与风险清点

**0.1 架构现状盘点**
- 任务：整理核心链路（登录、聊天、语音、订阅、评测）调用图。
- 产出：`app/docs/ARCH_BASELINE.md`（若超 500 行功能改动，需遵循 `app/AGENTS.md`）
- 验收：每条核心链路包含路由、服务、外部调用、DB 模型与缓存说明。

**0.2 风险清单**
- 任务：列出“启动失败点 / 高耦合模块 / 数据一致性风险”。
- 产出：`app/docs/ARCH_RISKS.md`
- 验收：风险包含影响面、触发条件、现有缓解方式与后续计划。

### 阶段 1：可观测性与安全日志

**1.1 Request-ID 全链路注入**
- 任务：新增中间件生成 request_id 并写入日志上下文。
- 涉及：`app/middleware/`、`app/core/logging.py`
- 验收：每条请求日志包含 request_id；无请求上下文时也不报错。

**1.2 错误日志脱敏**
- 任务：对请求头与请求体日志做脱敏（token、authorization、password、email 等）。
- 涉及：`app/middleware/error_handler.py`
- 验收：敏感字段只保留掩码或被移除；保留排障所需结构化信息。

**1.3 统一异常模型**
- 任务：引入统一业务异常基类（如 `AppError`），映射错误码与 HTTP 状态。
- 涉及：`app/middleware/error_handler.py`、`app/services/*`
- 验收：业务异常与系统异常可区分；响应格式稳定。

**1.4 Readiness/Health 接口**
- 任务：增加就绪探针（数据库、外部依赖可用性）与健康探针（进程可用）。
- 涉及：`app/main.py` 或新增 `app/api/health.py`
- 验收：就绪接口在依赖未就绪时返回非 200。

**1.5 外部依赖调用指标**
- 任务：对 LLM、GCS、Firebase、Google Play 调用添加耗时与失败率日志/指标。
- 产出：统一日志字段或 metrics stub（不强制引入新依赖）。
- 验收：可在日志中检索到“调用耗时、错误类型、上游耗时”。

### 阶段 2：配置与启动治理

**2.1 应用工厂模式**
- 任务：引入 `create_app()`，将 FastAPI 初始化与路由注册放入工厂函数。
- 涉及：`app/main.py`、新建 `app/app_factory.py` 或类似模块
- 验收：应用可通过 `create_app(config=...)` 启动；不依赖 import 副作用。

**2.2 配置加载下沉到启动阶段**
- 任务：将 `config.yaml` 加载从 import 时改为启动期执行；支持配置路径注入。
- 涉及：`app/core/config.py`、`app/main.py`
- 验收：无配置文件时不在 import 阶段崩溃，可通过启动参数控制。

**2.3 启动任务拆分与就绪控制**
- 任务：将预热任务拆分为可选执行，失败不影响进程启动但影响 readiness。
- 涉及：`app/main.py`、`app/services/cache_service.py`
- 验收：启动失败点可观测；不影响进程存活但 readiness 状态准确。

### 阶段 3：数据访问统一与依赖注入

**3.1 统一异步 DB Session**
- 任务：限制同步 `SessionLocal()` 的使用，仅保留在脚本或特殊场景。
- 涉及：`app/api/deps.py`、`app/db/session.py`
- 验收：路由与服务默认使用 AsyncSession。

**3.2 连接池与引擎配置归一**
- 任务：统一连接池创建逻辑，避免多套 pool 并存。
- 涉及：`app/db/*`、`app/core/agent/agent.py`
- 验收：数据库连接数可控；无重复 pool。

**3.3 外部服务依赖注入**
- 任务：将 `external_services/globals.py` 的全局单例改为依赖注入。
- 产出：`app/external_services/providers.py`（示例）
- 验收：可在测试中替换为 fake/Mock；生产通过配置注入。

### 阶段 4：后台任务与模块边界清理

**4.1 请求链路与后台任务解耦**
- 任务：将推送、缓存清理、重型 AI 调用剥离出请求链路。
- 选项：独立 worker 或轻量任务队列（先以不新增依赖为原则）。
- 验收：请求延迟降低；后台任务具备失败重试与告警策略。

**4.2 core/ 与 services/ 边界明确**
- 任务：定义模块边界规则（core 仅提供基础能力，services 仅编排业务）。
- 产出：`app/docs/ARCH_BOUNDARIES.md`
- 验收：跨层依赖减少；核心模块不再依赖业务服务。

**4.3 清理遗留配置与废弃项**
- 任务：删除已标记 DEPRECATED 的配置与代码路径。
- 验收：配置文件与代码中无死字段；部署配置清爽。

## 交付与验收标准

1. **功能稳定性**：核心接口无行为回归（聊天、订阅、语音、评测）。
2. **可观测性**：日志具备 request_id + 上游耗时 + 错误类型。
3. **可测试性**：关键依赖可注入 fake/mock；测试不依赖真实外部服务。
4. **可靠性**：Readiness 与 healthz 区分明确，启动失败原因可识别。

## 风险与缓解

- **风险：启动逻辑改动导致服务无法启动**
  - 缓解：先引入工厂模式并保持旧入口兼容；分阶段切换。
- **风险：同步 DB 清理导致阻塞路径隐藏**
  - 缓解：增加 async 替代实现并保持短期兼容。
- **风险：日志脱敏影响排障**
  - 缓解：保留结构化字段与摘要信息，不记录原始敏感值。
