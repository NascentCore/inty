# 数据库只读副本迁移清单（按优先级递减）

## 目标与原则

- 目标：将 `app/` 中可容忍复制延迟（eventual consistency）的读请求迁移到只读副本，降低主库读压力。
- 原则：
  - **读写分离**：读走 replica，写始终走主库。
  - **在线链路优先稳定**：涉及实时 read-after-write 的接口暂不迁移。
  - **可回滚**：每一批改动都可通过依赖注入或配置开关快速回退到主库读取。
  - **先离线后在线**：先迁移离线/运营分析任务，再评估低风险在线读。

## P0（最高优先级）：运营分析读接口全量切副本（已完成）

### 范围

- 文件：`app/api/v1/endpoints/evaluation.py`
- 目标：将大部分 `/user-analytics/*` 读接口从 `Depends(deps.get_async_db)` 切换为 `Depends(deps.get_async_replica_db)`。

### 重点迁移项

- 已经在副本上的接口保持不变：
  - `/user-analytics/reports`
  - `/user-analytics/image-generation-failures`
- 其余统计类、趋势类、列表类 user-analytics 接口按批次切换副本依赖。

### 原因

- 属于超级用户运营分析页面，非用户实时交互主路径。
- 对“刚写入立刻可见”要求较低，适合容忍副本延迟。

### 风险与控制

- 风险：副本延迟导致分析页面短时不一致。
- 控制：
  - 接口说明中注明“数据可能有几秒到几十秒延迟”。
  - 副本异常时可临时切回主库依赖（快速回滚）。

### 验收

- 各 analytics 页面可正常加载。
- 主库 CPU/IO 峰值下降，副本读流量上升。

## P1：离线记忆抽取任务迁移到副本读（已完成）

### 范围

- 调度入口：`app/services/push_scheduler_service.py`
  - `_run_memory_extraction`
- 逻辑文件：`app/services/memory_extraction_service.py`
  - `get_users_to_extract`
  - `get_all_messages_for_user`
  - `_compute_users_to_extract_sync`

### 迁移策略

1. 为记忆抽取增加“读会话/连接来源”参数（主库或副本）。
2. `subscription_usage` 聚合与 `chat_history` 历史读取优先走副本。
3. `memory`、`memory_extraction_log` 写入仍走主库事务。

### 原因

- 该任务为每日离线批处理，天然可接受最终一致。
- 读量大（会扫 `subscription_usage` + `chat_history`），迁移收益明显。

### 风险与控制

- 风险：副本延迟导致“候选用户”少量滞后。
- 控制：
  - 次日任务可补齐，不影响最终结果。
  - 增加日志字段：本次候选用户数、副本延迟观察值（如可获取）。

### 验收

- 任务总耗时可接受。
- 与主库跑数对比，核心指标偏差在可接受范围内。

## P1：节日记忆抽取（定时 + 手动）迁移到副本读（已完成）

### 范围

- 调度：`app/services/push_scheduler_service.py`
  - `_run_festival_memory_extraction`
- 手动执行接口：`app/api/v1/endpoints/festival_memory.py`
  - `/festival-memory-extraction/run`
- 服务：`app/services/festival_memory_service.py`
  - `get_pairs_with_min_rounds_in_window_sync`
  - `get_messages_for_user_agent_sync`

### 当前问题

- 当前显式使用 `database.url`（主库）做读取与筛选，读压力集中在主库。

### 迁移策略

1. 增加 `database.replica_*` 对应的同步连接 URL（或复用已有转换逻辑）。
2. 优先用副本执行 pairs 筛选与消息读取。
3. 写入 `memory`、更新状态字段继续走主库。
4. 若副本不可用，按策略降级主库（带告警）。

### 原因

- 任务属于运营/离线流程，可容忍延迟。
- 高频扫描（5 分钟）下，主库读压优化价值高。

### 验收

- 定时抽取成功率不下降。
- 主库读取量明显下降。

### 执行记录（2026-02-15）

- 状态：✅ 已完成

- 迁移范围：

## P2：Push 扫描任务中的“发现类读”迁移

### 范围

- 调度：`app/services/push_scheduler_service.py`
  - `_discover_new_users`
  - `_discover_users_with_updated_tokens`
- 服务：`app/services/push_notification_service.py`
  - `discover_new_users_for_push`
  - `discover_users_with_updated_tokens`

### 迁移策略

- 发现类查询（扫描用户、token 状态）走副本。
- 最终状态更新（如清理 `fcm_token_invalid_at`）保持主库。
- 必要时采用“副本读 + 主库写前再校验一次”避免误更新。

### 原因

- 小时级任务，延迟容忍度高。
- 读多写少，适合副本承接。

### 风险与控制

- 风险：副本延迟造成误判（例如刚更新 token 但副本未同步）。
- 控制：写前主库二次确认关键条件。

## P3（低优先级，谨慎）：可读写混合服务的局部读拆分

### 候选

- `push_notification_service` 中非去重关键路径的纯查询子函数
- `chat_history_service` 中仅后台排查用途的只读函数

### 不建议立即迁移的部分

- 在线聊天主链路：
  - `get_messages_paginated`
  - `get_history_messages`
  - `get_last_message_with_timestamp`
- 推送去重/防重核心查询：
  - `has_sent_push_for_stage`
  - `get_users_needing_push`
  - 其他依赖“最新状态”的判断逻辑

### 原因

- 以上路径对 read-after-write 敏感，副本延迟会放大重复推送、会话不一致等风险。

## 批次执行建议（推荐顺序）

1. **批次 A（低风险高收益）**：P0 user-analytics 接口依赖切换到 replica。
2. **批次 B（离线大读）**：P1 记忆抽取迁移。
3. **批次 C（离线大读）**：P1 节日记忆抽取迁移。
4. **批次 D（发现类任务）**：P2 push 发现任务迁移并加主库写前校验。
5. **批次 E（可选优化）**：P2/P3 候选项按收益逐步推进。

---

## 每批通用验收与回滚

### 验收指标

- 主库：QPS/CPU/IO/慢查询下降。
- 副本：读流量上升但无长时间积压。
- 业务：任务成功率、接口错误率、P95/P99 响应时间稳定。

### 回滚策略

- API 层：将 `deps.get_async_replica_db` 改回 `deps.get_async_db`。
- 服务层：副本会话创建失败时降级主库（并记录告警日志）。
- 调度层：可按任务级别临时关闭迁移路径，仅保留主库读。
