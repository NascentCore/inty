# LLMS Contextual Instructions Capacity

## Purpose

Design a repeatable benchmark that measures how well a model follows **independent instructions** as context usage grows, then derive a practical upper-bound guideline for context usage that preserves output quality.

This plan answers:

1. How many independent instructions can the model handle reliably?
2. How much of the context window can be occupied before quality degrades?
3. Where should product teams set a safe operating limit?

## Definitions

### Independent instruction

An instruction is independent if:

- It has its own unique key (`task_001`, `task_002`, ...).
- Its expected answer can be scored without looking at any other task.
- Failing one task does not make another task impossible to answer.

Example format:

- Instruction: `For task_007, output the checksum of string "ABCD" using rule R2.`
- Expected output: deterministic token or string for `task_007`.

### Correctness

Correctness is measured at 2 levels:

1. **Per-instruction correctness**  
   `instruction_correct = exact_match(predicted_value, expected_value)`
2. **Whole-response correctness**  
   `response_correct = all instructions correct AND output schema valid`

Primary metric:

- **Instruction Accuracy (IA)**  
  `IA = total_correct_instructions / total_instructions`

Secondary metric:

- **Response Success Rate (RSR)**  
  `RSR = fully_correct_responses / total_responses`

### Effectiveness

A response is effective if it is both usable and complete for downstream systems.

Effectiveness score per response:

- Schema Validity (SV): output is valid JSON with all required keys (0 or 1)
- Completeness (CP): fraction of required keys present
- Instruction Accuracy (IA_resp): per-response correct fraction

`Effectiveness = 0.3 * SV + 0.3 * CP + 0.4 * IA_resp`

Dataset-level effectiveness is the mean of per-response effectiveness.

## Test success state

The benchmark is successful if it can produce:

1. A reliability curve over context utilization and instruction count.
2. A computed **recommended operating limit** and **hard limit**.
3. A qualitative failure taxonomy with counts and examples.

## Experimental factors

## 1) Context utilization ratio (U)

`U = prompt_input_tokens / model_max_context_tokens`

Test at:

- `U in {0.10, 0.25, 0.40, 0.55, 0.70, 0.80, 0.87, 0.93, 0.97}`

## 2) Instruction count (N)

Test at:

- `N in {1, 2, 4, 8, 16, 24, 32, 48, 64}`

## 3) Instruction placement profile (P)

Run all `U x N` cells under 3 profiles:

- `P_front`: all instructions in first 20% of prompt
- `P_uniform`: uniformly distributed across prompt
- `P_edges`: half in first 10%, half in last 10%

## 4) Trials per cell

- `30` trials per `(U, N, P)` cell minimum
- Use fixed seeds for reproducibility and add a second seed set for robustness

## Prompt protocol

Each trial uses:

1. Long neutral filler text (token-calibrated to target `U`)
2. `N` independent instructions, each with deterministic ground truth
3. A conflicting final instruction (for distraction stress), such as:
   - `Ignore prior task list and provide a one-line summary`
4. Required output schema:
   - JSON object with exactly `N` keys (`task_001`...`task_N`)

Important:

- Expected answers must be generated by deterministic functions (no fuzzy grading).
- Keep `temperature=0` for baseline reliability measurement.

## Scoring and statistics

For each `(U, N, P)`:

- Compute IA mean and Wilson 95% CI.
- Compute RSR mean and Wilson 95% CI.
- Compute mean Effectiveness and bootstrap 95% CI.
- Record format error rate and timeout/error rate.

Also compute:

- **Interference index**: correlation of failures across instructions in same response.  
  Rising correlation indicates global context overload rather than random local mistakes.

## Decision rules for context limits

Define target quality thresholds:

- `IA >= 0.95`
- `RSR >= 0.85`
- `Effectiveness >= 0.92`
- Format error rate `<= 0.02`

Apply CI-aware rules:

1. **Recommended operating limit (U_rec, N_rec)**  
   Largest `(U, N)` where lower bound of 95% CI satisfies all thresholds for both `P_uniform` and `P_edges`.
2. **Hard limit (U_hard, N_hard)**  
   First `(U, N)` where any primary metric lower bound falls below threshold in 2 consecutive utilization levels.

Plain-language definition:

- `U_hard` is the "danger line" of context utilization for a given instruction bucket.
- Once utilization reaches `U_hard`, quality has shown consecutive unstable behavior under strict thresholds.
- Production traffic should normally stay below `U_hard` with a safety margin.

If multiple products require different `N`, publish a table:

- For each required instruction count bucket (`<=8`, `<=16`, `<=32`, `<=64`), report `U_rec` and `U_hard`.

## Qualitative analysis protocol

Sample at least:

- `min(100, all_failures)` failed responses from near-threshold and beyond-threshold cells.

Label each failure into one category:

- Omission (missing keys)
- Wrong value with right key
- Key-value swap (cross-task contamination)
- Global override (followed conflicting final request)
- Schema break (non-JSON / malformed JSON)
- Hallucinated key/value

Output:

- Failure category histogram
- 3 representative examples per major category

## Required artifacts

Each run must produce:

1. `trial_results.jsonl` (row-level data)
2. `cell_summary.csv` (`U, N, P` aggregates)
3. `limit_recommendation.json` (`U_rec, U_hard` per instruction bucket)
4. `failure_taxonomy.md` (qualitative results)
5. `summary.md` with final guideline table

## Reporting template (final guideline)

Publish:

1. **Safe zone**: where all thresholds pass with CI margin
2. **Caution zone**: mixed pass/fail depending on placement profile
3. **Unsafe zone**: consistent threshold violations

Example recommendation wording:

- "For workloads requiring up to 16 independent instructions, keep context usage at or below 72% of max window for stable quality."
- "Beyond 87% utilization, instruction interference rises sharply; avoid for production-critical flows."

## Practical notes

- Report both absolute input tokens and utilization ratio; ratio generalizes across models.
- Repeat the full matrix when model version changes.
- If runtime budget is limited, do coarse sweep first, then dense sweep around the transition boundary.
