# 两步结构化桥接：用「中间表示 + 物化器」提升 LLM 产出质量

**一句话**：让模型只负责在**窄 schema** 里做决策，把「落到真实世界」交给**可测试、可回放**的第二步程序，用来降低歧义、便于校验、并抑制长链迭代里的误差放大。

## 这是什么、和谁相关

- **意图**：LLM 擅长语义与策略，但在需要**精确参数、可组合原语、副作用可控**的场景里，若直接把自由自然语言当作最终执行载体，容易出现解析漂移、不可验证、以及「一步错、步步修」的崩塌。
- **做法**：拆成固定两步：
  - **第一步（生成）**：模型输出**结构化中间表示**（IR），例如 JSON / 命令列表 / 固定枚举 + 数值字段，而不是最终像素、SQL 字符串碎片、或未经约束的长文。
  - **第二步（物化）**：受信任的代码**校验、归一化、再执行**（渲染、调用 API、写迁移、跑工具），对同一 IR 的行为应**确定、可重复**（随机性若存在，应显式、可种子化、可记录）。
- **适用人群**：设计 agent 工具协议、画布/几何/布局类功能、运维变更、数据写入、任何「说错一个数就全毁」的管线时，用来对齐产品预期与工程可控性。

## 何时值得用

- **高歧义域**：坐标、时间、金额、标识符、权限边界等，需要与真实系统的字段一一对应。
- **组合敏感**：多步叠加后质量断崖（composition / 误差累积），需要把每步约束在**小词汇表的原语**上。
- **需要证据链**：审计、回放、调试时，要能保存「模型当时到底提交了什么 IR」，而不是事后从长文里猜。
- **与人机闭环配合**：IR 可被 UI 预览、diff、拒绝、或部分采纳，再进入物化。

## 何时不必用

- **探索性对话**、一次性摘要、创意发散：强加 schema 只会拖慢迭代。
- **IR 已经等价于另一套自然语言**（字段过多、自由文本槽位过大）：schema 失去约束力，两步退化为「套壳散文」。

## 设计要点（抽象规则）

- **窄原语集**：允许的操作类型要少、语义清晰（例如 line / arc / circle，而不是「随便描述一笔」）。
- **硬校验**：类型、范围、枚举、互斥字段；失败时**拒绝执行**并返回可消费的纠错信号，而不是静默修补到面目全非。
- **物化器单一真相**：渲染/执行逻辑以代码为准；文档只描述**意图与边界**，不逐字段复述实现细节（实现细节在类型定义与测试里）。
- **随机性显式**：若物化阶段需要随机（纹理、采样），**参数与种子策略**应可配置或可从 IR 复现；不要把「看起来像随机」藏在黑盒里又声称可审计。
- **闭环可选**：生成器若能读取**上一步物化后的状态**（图像、数据库快照、CI 日志）再产出下一批 IR，属于在此模式上的增强；核心仍是「先生成 IR，再确定性落地」。

## 反模式

- **把自然语言嵌进 IR 的每个字段当「说明文」**：执行端若再次依赖 LLM 去「理解说明」，两步优势消失。
- **无版本 schema**：线上 IR 与物化器漂移后，旧作品/旧任务无法解释。
- **物化器默默容错**：把非法坐标钳制、把非法颜色换成默认色，会掩盖模型问题并制造「灵异」行为。

## 与其他模式的关系

- **工具调用（function calling）**：常已是「模型产结构化参数 + 运行环境执行」；本指南强调的是**刻意收窄参数空间**与**物化阶段的可验证性**，不仅限于单次 tool call。
- **ReAct / 多步 agent**：每一步仍可遵守本模式；关键是**每步对外部世界的写入**尽量经由 IR，而不是长文本直接驱动副作用。

## 落地检查清单

- IR 是否可被 **JSON Schema / Pydantic / TypedDict** 一类机制静态描述？
- 物化器是否有**单元测试**覆盖典型 IR 与非法 IR？
- 产物是否可 **保存 IR + 保存物化结果** 以便复现与排障？
- 产品是否允许 **预览 / 拒绝 / 重试** 单批 IR，而不是全有或全无？

## 动机示例（域外引用，非本仓库实现）

- 迭代绘画类应用：VLM 产出笔划对象（线、弧、折线等），宿主程序负责光栅化到画布；随机纹理若存在，由渲染器在受控参数下完成。该分工体现「语义与布局决策」与「像素级执行」分离，便于回放与定位坏笔划。
